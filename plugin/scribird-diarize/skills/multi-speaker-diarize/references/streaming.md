# S3를 쓰지 않는 방법 — 스트리밍 구현

## 왜 직접 짰는가

배치 API는 `Media.MediaFileUri`로 `s3://` URI만 받는다. 로컬 파일을 넘기는 필드가 없어서,
분석하려면 버킷을 만들고 업로드해야 한다. 출력 버킷(`--output-bucket-name`)은 생략할 수
있지만 **입력은 아니다.**

스트리밍은 오디오를 WebSocket으로 직접 흘려보내므로 버킷이 필요 없다. 대가는 세 겹을
직접 구현하는 것이다.

| 겹 | 모듈 | 왜 직접 |
|---|---|---|
| WebSocket (RFC 6455) | `awsstream/websocket.py` | stdlib에 클라이언트가 없다 |
| 이벤트 스트림 프레이밍 | `awsstream/eventstream.py` | AWS 고유 바이너리 형식 |
| SigV4 롤링 서명 | `awsstream/sigv4.py` | 청크마다 직전 서명이 입력 |

`aws transcribe-streaming` CLI 명령은 **존재하지 않는다**(확인함). boto3를 쓰면 위 세
겹이 사라지지만 `pip install`이 필요해지고, 그러면 `/usr/bin/python3`에서 그냥 도는
성질을 잃는다. 그 성질이 세 겹을 짤 값이라고 판단했다.

## 실측한 함정

**서명하는 `host`에서 포트를 빼야 한다.** 접속은 8443으로 하는데 서버는 포트 없는
호스트명으로 서명을 계산한다. 포트를 넣어 서명하면 `InvalidSignatureException`이 오고,
그 메시지에 서버가 기대한 canonical string이 담겨 온다 — 실측에서 그 `host:` 행이
`transcribestreaming.us-east-1.amazonaws.com`(포트 없음)이었다. 접속 URL과 서명 대상이
갈린다는 것이 요점이다.

> 이 오류를 찾은 방법도 기록해 둔다. 프레임을 몇 개 보낸 뒤 **읽어야** 예외가 보인다.
> 계속 보내기만 하면 서버가 연결을 끊고 `BrokenPipeError`만 남아, 원인이 서명인지
> 네트워크인지 알 수 없다.

**빈 페이로드 프레임이 스트림의 끝이다.** 이걸 보내지 않고 소켓을 닫으면 서버가 마지막
발화를 확정하지 않고 세션을 버린다.

**서명 헤더는 bytes다.** `:chunk-signature`를 hex 문자열로 넣으면 서명 불일치로 끊긴다.
이벤트 스트림 헤더 타입 6(bytes)과 7(string)의 인코딩이 다르다.

**CRC는 CRC32(zlib)다.** AWS 문서가 "CRC32"라고만 적어 혼동하기 쉬운데, S3 체크섬의
CRC32C(Castagnoli)와 다항식이 다르다. 잘못 쓰면 서버가 조용히 프레임을 버린다.

**한 WebSocket 프레임에 이벤트 스트림 메시지가 여러 개 온다.** 첫 개만 읽고 버리면
전사 결과가 조용히 사라진다 — 결과가 적게 나오는 방식으로 실패해 알아채기 어렵다.

## 배치와 갈리는 두 가지

| | 스트리밍 | 배치 |
|---|---|---|
| 화자 수 상한 | 지정 불가, 최대 10명 | `MaxSpeakerLabels` 2~30 |
| 다국어 | 언어 하나만 | `IdentifyMultipleLanguages` |

그래서 배치를 지우지 않고 남긴다. 참석자가 10명을 넘거나 한·영이 비슷한 비중으로 섞인
회의는 배치가 필요하다.

실측 비교(같은 오디오 120초, AWS Events 세션):

| | 스트리밍 | 배치 |
|---|---:|---:|
| 감지 화자 | 4명 | 3명 |
| 화자 구간 | 19개 | 13개 |
| S3 객체 | 0 | 생성 후 삭제 |

화자 수가 다른 것은 어느 쪽이 틀린 것이 아니라 다른 모델 구성이다. 스트리밍이 더 잘게
나누는 경향이 있으니, 결과를 보고 사용자가 판단하게 한다.

## 출력 형식을 배치에 맞춘 이유

`merge_speakers.py`는 배치 JSON을 읽도록 만들어져 있고 그쪽에 테스트가 붙어 있다.
스트리밍용 병합 경로를 따로 만들면 같은 로직이 두 벌이 되고, 한쪽만 고쳐지는 사고가
난다. 그래서 스트리밍 결과를 배치 형태로 바꿔서 넘긴다.

바꿔야 하는 차이:

| | 배치 | 스트리밍 |
|---|---|---|
| 화자 라벨 | `speaker_labels.segments[]` | 항목마다 `Speaker` |
| 라벨 값 | `spk_0` | `0` |
| 시각 | 문자열 `"1.23"` | 숫자 `1.23` |

스트리밍에는 화자 구간 목록이 없으므로 연속된 같은 화자의 항목을 묶어 만든다. 단어마다
구간을 만들면 병합 쪽 겹침 계산이 조각난 구간과 대조하게 되어 배정률이 떨어진다.

## 오디오 변환

`afconvert`로 16kHz 모노 16-bit PCM으로 바꾼다. macOS에 항상 있어서 추가 설치가 필요
없다.

모노인 이유는 채널 분리(`ChannelIdentification`)와 화자 분리를 **동시에 쓸 수 없기**
때문이다 — 우리가 원하는 것은 화자 분리다. 16kHz인 이유는 전사 모델이 내부적으로 그
레이트를 쓰므로 그 이상은 대역폭만 늘린다.

**WAVE 헤더 길이를 44바이트로 가정하지 않는다.** `afconvert`가 `LIST`나 `fact` 청크를
함께 넣으면 그만큼 밀리는데, 고정 길이로 자르면 헤더 조각이 오디오로 해석돼 맨 앞에
잡음이 섞인다. 전사 첫 단어가 이상해지는 방식으로 나타나 원인을 찾기 어렵다.

## 전송 속도

100ms 프레임을 실시간의 10배 속도로 보낸다(2분 오디오 → 약 12초). 파일 전체를 한 번에
쏟으면 서버가 스로틀링하거나 연결을 끊는다. 완전히 지연 없이 보내는 것보다 느리지만,
중간에 끊겨 처음부터 다시 하는 것보다 빠르다 — 롤링 서명 체인 때문에 중간부터 이어붙이는
재연결은 존재할 수 없다.
